Conventions: `<WL_KC>` = workload cluster kubeconfig, `<MGMT_KC>` = management, `<MACHINE_NS>` = Machines' namespace, controller logs via `kubectl --kubeconfig <MGMT_KC> -n longhorn-capi-system logs deploy/longhorn-capi-eviction-controller`. ### S1 — happy-path regression (required)

**Setup:** 3-worker Longhorn workload cluster; a writer Deployment (2 or 3 replicas volume) with a probe file:

```bash
kubectl --kubeconfig <WL_KC> -n default exec deploy/writer -- \
  sh -c 'printf "longhorn-capi-review-2026-09-30" > /data/probe.input && md5sum /data/probe.input > /data/probe.md5 && cat /data/probe.md5'
# record the md5
```

**Trigger:** `kubectl --kubeconfig <MGMT_KC> -n <MACHINE_NS> delete machine <WORKER_MACHINE>`

**Expected (controller logs, in order):**
1. `Registered Longhorn pre-terminate hook`
2. `Triggering Longhorn eviction`
3. `Longhorn eviction complete — releasing hook` (or Early-release path: `Early release: ... releasing hook`)
4. Machine object disappears; replacement Machine joins (`Ready`); volume `robustness=healthy`
5. Data intact: `kubectl -n default exec deploy/writer -- cat /data/probe.md5` → md5 matches; `md5sum -c /data/probe.md5` clean.

**PASS:** all five; event `LonghornEvictionComplete` (or `LonghornEarlyRelease`) on the Machine; zero `LonghornEvictionTimeout` events.

### S2 — last-live-replica protection (required — CRIT-1)

**Setup:** a replica-1 volume pinned to a known worker:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: longhorn-rep1-test
provisioner: driver.longhorn.io
parameters:
  numberOfReplicas: "1"
reclaimPolicy: Delete
volumeBindingMode: Immediate
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: rep1-data
  namespace: default
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: longhorn-rep1-test
  resources:
    requests:
      storage: 2Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rep1-writer
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels: {app: rep1-writer}
  template:
    metadata:
      labels: {app: rep1-writer}
    spec:
      containers:
        - name: writer
          image: busybox:1.36
          command: ["sh", "-c", "printf 'rep1-probe' > /data/probe.input && md5sum /data/probe.input > /data/probe.md5 && sleep 3600"]
          volumeMounts:
            - {name: data, mountPath: /data}
      volumes:
        - name: data
          persistentVolumeClaim: {claimName: rep1-data}
```

Locate the replica's node, then delete THAT node's Machine:

```bash
kubectl --kubeconfig <WL_KC> -n longhorn-system get replicas \
  -o custom-columns=NAME:.metadata.name,ENGINE:.spec.engineName,NODE:.spec.nodeID
# find the Machine whose status.nodeRef.name == that node:
kubectl --kubeconfig <MGMT_KC> -n <MACHINE_NS> get machines -o custom-columns=NAME:.metadata.name,NODE:.status.nodeRef.name
kubectl --kubeconfig <MGMT_KC> -n <MACHINE_NS> delete machine <THAT_MACHINE>
```

**Expected:**
1. Controller log at least once during the rebuild window: `Refusing to delete a volume's last live replica`
2. The volume's only replica is **never deleted by the controller** — Longhorn's own eviction rebuilds it onto a surviving node (volume briefly `degraded`, then `healthy` at 1 replica elsewhere)
3. Hook released normally (`LonghornEvictionComplete`); replacement joins; `md5sum -c /data/probe.md5` inside `deploy/rep1-writer` clean.

**PASS:** all three. **Known-limit note:** if no viable rebuild target exists (all other nodes unschedulable/full), Longhorn cannot migrate a last replica and the `--eviction-timeout` backstop (30m in this test) releases anyway — volume faults by design of the backstop. That is a report item, not a controller bug.

### S5 — EvictStuckPods (opportunistic + assertions)

**Setup:** during S1, also run on the departing node: (a) the Longhorn-PVC writer, and (b) a pod using a **non-Longhorn** PVC (e.g. the k8s local-path provisioner) so both kinds are present.

**Assertions (check regardless of whether the natural stall occurs):**
- Any controller log line `EvictStuckPods: force-deleted Longhorn-PVC pods` lists **only** pods whose PVCs resolve to Longhorn Volume CRs — the local-path pod must never appear.
- No pod is force-deleted while any of its Longhorn volumes is FAULTED (unit tests cover this; assert from events if observed).
- If CAPI does stall at `WaitingForVolumeDetach`: node gets cordoned (`SchedulingDisabled`), listed pods disappear promptly (grace period 0 — no long-`Terminating` hang), machine delete completes.

**PASS:** assertions hold across the run; no unrelated workload deleted by this controller. (CAPI's own drain may still evict pods — that's not this controller; distinguish by the log line.)
